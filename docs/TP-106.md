# TP-106 — Asynchronous ERP supplier catalog synchronization

## Goal

Move supplier catalog imports off the HTTP/request path and process them with Symfony Messenger. The handler reuses the TP-103 importer and TP-104 job tracker. Transient infrastructure errors are deliberately allowed to bubble up so Messenger can retry them.

## Flow

1. The application creates an import job with `ImportJobTracker::start()`.
2. The caller dispatches `SyncSupplierCatalogMessage(jobId, source, rows)` through the configured Messenger bus.
3. The worker validates payload rows using `SupplierImportRowFactory`.
4. Valid rows are imported in bounded DAL batches; row-level validation failures are counted as rejected.
5. The job tracker records the result after successful processing.
6. Transport/infrastructure exceptions escape the handler and are retried according to the configured backoff. After retries are exhausted, Messenger moves the message to the `failed` transport.

## Configuration

The root `config/packages/messenger.yaml` defines an AMQP-backed `async` transport and a Doctrine `failed` transport. Set `MESSENGER_TRANSPORT_DSN` in local environment configuration; do not commit real credentials. The sample DSN assumes the Compose service is named `queue` and the default AMQP virtual host is used—adjust it to match your environment.

Run a worker inside the Shopware container:

```bash
bin/console messenger:consume async -vv --time-limit=3600 --memory-limit=256M
```

Inspect failed messages:

```bash
bin/console messenger:failed:show
bin/console messenger:failed:retry --force
```

Check the installed Symfony version and Doctrine Messenger transport support before enabling the failed transport. The Doctrine transport may require an available DBAL transport dependency/table setup; if unavailable, configure a separate AMQP failure queue instead.

## Important production notes

- Messages currently carry row payloads for this exercise. Keep batches small; for large files, persist source data and send only an immutable batch ID.
- The job must exist before dispatch. A dispatch failure should mark or reconcile the job rather than leave it permanently Running.
- Retried messages can execute more than once. Writes must be idempotent; the current supplier key-to-ID strategy from TP-102/103 needs review before production.
- The handler only marks completion after the import call returns. Exhausted retries should be correlated with the failed transport and job ID; a dedicated failure handler/monitoring ticket is still needed.
- Validate that the root Messenger config merges cleanly with the existing Shopware project config before deployment.
- Tests and worker execution have not been run against the live Docker environment as part of this commit.

## Acceptance criteria

- The message is serializable and validates its required fields.
- The handler reuses the application import service rather than duplicating DAL rules.
- Transient repository/transport failures are not swallowed by the handler.
- Retry/backoff and a failed-message transport are configured centrally.
- Batch size is bounded to avoid unbounded DAL operations.
